## Главное, что нужно понять до начала работ

**Контейнер Linux не может управлять Windows-машиной.**

Это не настройка, которую можно поменять, а устройство: контейнер исполняется внутри
Linux-виртуалки Docker Desktop, а не как процесс Windows.

| Что | Доступно контейнеру |
|---|---|
| Windows PowerShell, cmd | нет |
| Службы Windows, реестр | нет |
| Диск `C:` | только явно проброшенные папки |
| `localhost` | это сам контейнер, не машина |

**А бот Claude+Telegram существует именно ради управления этой машиной.** Он запускает
PowerShell, правит службы, ходит по диску. В контейнере он будет управлять пустым
контейнером — то есть перестанет делать то, ради чего создан.

### Вывод

```
Claude+Telegram  →  остаётся нативным (служба Windows)
Hermes           →  в контейнер
OpenClaw         →  в контейнер
Marketing agency →  в контейнер
Knowledge Factory→  в контейнер
```

Это не компромисс, а следствие назначения. Бот — точка входа в саму машину; остальные
проекты машиной не управляют, им контейнер подходит.

## Пять конфликтов, которые реально будут

Ваше опасение верно, но конфликты конкретные и перечислимые.

### 1. Один токен Telegram на два процесса — неустранимый

Telegram не даёт двум процессам читать сообщения одного бота: второй получает
`409 Conflict`. Это устройство API, а не настройка.

**Уже проявилось:** официальный плагин `telegram` не работает именно поэтому.

**Лечение:** каждому боту свой токен от `@BotFather`. Контейнер не поможет — конфликт
происходит на стороне Telegram.

### 2. Порты хоста общие даже у изолированных контейнеров

Опубликованный порт занимает его на всей машине. Два проекта не смогут оба слушать
`8080`. У бота уже задан `API_SERVER_PORT=8080`, у Hermes свой gateway.

**Лечение:** разные порты, либо не публиковать внутренние службы наружу, либо
маршрутизирующий прокси перед ними.

### 3. Общий профиль `~/.claude` — самый коварный

Все проекты читают один профиль: одни MCP-серверы, одна авторизация, одни настройки.
Именно поэтому Anthropic в своём эталоне создаёт **отдельный том на каждый репозиторий**.

**Частично закрыто** файлом `.mcp.json` в проекте. Полностью снимается разделением
профилей по контейнерам.

### 4. Глобальные имена контейнеров и томов

`container_name: claude` или жёсткое имя тома в двух проектах — столкновение. Глобальные
имена обходят изоляцию Compose.

**Лечение:** не задавать их вручную, позволить Compose добавлять префикс проекта.

### 5. Память и процессор

Hermes, четыре агента Marketing agency, Knowledge Factory с postgres, qdrant и minio —
это около десятка контейнеров. Конфликт ресурсный, а не логический.

## Как устроен правильный контейнер для Claude Code

У Anthropic есть официальный эталон: `github.com/anthropics/claude-code/tree/main/.devcontainer`

Anthropic прямо говорит: это **рабочий пример, а не поддерживаемый базовый образ** — его
копируют и адаптируют.

| Файл | Роль |
|---|---|
| `devcontainer.json` | непривилегированный пользователь, монтирование только исходников, отдельные тома под историю и профиль |
| `Dockerfile` | Node 20, git, gh, zsh, jq, iptables — и установка Claude Code |
| `init-firewall.sh` | исходящий трафик: запрещено всё, кроме явно разрешённого |

**Ключевая деталь:** том с профилем создаётся с суффиксом идентификатора контейнера. Это
и есть механизм, не дающий проектам делить авторизацию.

Плюс задаётся `CLAUDE_CONFIG_DIR`, иначе часть состояния осядет мимо тома.

### Честные пределы встроенного файрвола

Скрипт разрешает GitHub, npm, `api.anthropic.com` и телеметрию, остальное запрещает. Но
это **не полноценный доменный фильтр**:

- DNS и SSH разрешены широко
- подсеть хоста разрешена целиком
- домены превращаются в адреса один раз при старте
- фильтрация по адресу, а не по имени в TLS
- права `NET_ADMIN` и `NET_RAW` сами ослабляют границу контейнера

Anthropic отмечает: эти права нужны **их скрипту**, а не Claude Code. Можно их не давать,
а ограничивать трафик снаружи. В серьёзных внедрениях так и делают — файрвол внутри
контейнера администрируется изнутри той же границы, которую охраняет.

### Авторизация

| Способ | Когда | Переживает перезапуск |
|---|---|---|
| **Именованный том под `~/.claude`** | подписка Pro/Max | да, до удаления тома |
| Привязка папки хоста | нужен доступ снаружи | да, но отдаёт учётные данные контейнеру |
| `ANTHROPIC_API_KEY` | оплата по API | да, если секрет подставляется |
| `CLAUDE_CODE_OAUTH_TOKEN` | подписка в CI | токен на год |

**Рекомендация:** именованный том. Залогиниться один раз внутри контейнера, дальше сессия
живёт в томе.

**Предупреждение из документации:** учётные данные внутри контейнера доступны агенту
целиком. Флаг пропуска подтверждений не защищает от вредоносного репозитория.

## Связь между проектами без смешивания

Механизм — **внешние сети Docker**. Каждому проекту своя сеть; общая служба подключается
к нескольким сразу.

```
сеть проекта A ──┐
                 ├── общая служба (MCP-шлюз, кэш)
сеть проекта B ──┘
```

Проект A видит общую службу. Проект B видит общую службу. **Друг друга они не видят.**

Правила, делающие это надёжным:

- у каждого проекта явное имя проекта, иначе Compose возьмёт имя папки
- никаких глобальных имён контейнеров и жёстких имён томов
- у каждого проекта свой том под профиль Claude
- общая служба не должна включать пересылку пакетов, иначе свяжет проекты
- внешние сети не удаляются командой остановки — их жизненным циклом управляют отдельно

## Если контейнеру нужно что-то сделать на Windows

Четыре способа, по убыванию риска.

### А. Проброс сокета Docker — не рекомендую

Контейнер получает управление движком Docker. Документация Docker прямо приравнивает это
к выдаче административных прав и предупреждает, что изоляция ломается.

### Б. Посредник на стороне хоста — рекомендую

Небольшая служба Windows с авторизованным интерфейсом; контейнер обращается к ней через
`host.docker.internal`.

Она выполняет **не произвольные команды**, а разрешённый список операций: перезапустить
службу, собрать журнал, запустить проверку.

Промышленный вариант добавляет: взаимную аутентификацию или короткоживущие токены, списки
разрешённых команд и путей, отдельную непривилегированную учётную запись, тайм-ауты,
структурированные аргументы вместо строк оболочки, полный журнал вызовов.

### В. SSH обратно на Windows

Поднять OpenSSH Server на машине, подключаться из контейнера. Microsoft документирует
PowerShell remoting поверх SSH. Нужен отдельный ключ и ограниченная учётная запись.

### Г. Очередь заданий

Контейнер пишет запросы в общую папку, служба Windows их проверяет и выполняет. Медленнее,
зато полностью проверяемо и протоколируемо.

## Управление Claude Code из Telegram — два разных механизма

### Механизм 1 — ваш нынешний бот

```
Telegram → бот → запускает НОВЫЙ процесс claude.exe → ответ → Telegram
```

Каждое сообщение — отдельный запуск. Ваш чат в браузере и чат с ботом — разные сессии,
они друг друга не видят.

**Плюс:** работает круглосуточно как служба Windows.

### Механизм 2 — то, что обычно и хотят

```
Telegram → подключение к УЖЕ ИДУЩЕЙ сессии → та же сессия
```

Это официальный плагин `telegram@claude-plugins-official`. Он **установлен, но отключён**:
токен из него убран, чтобы не ловить `409 Conflict` с основным ботом.

Именно он передаёт написанное в Telegram в текущую сессию.

**Что нужно:**
1. Завести второй бот в `@BotFather` — отдельный токен
2. Прописать токен в `~\.claude\channels\telegram\.env`
3. Запускать сессию с указанием канала

**Чего не даст:** сессия живёт, пока запущен Claude Code. Закрыли терминал — канал молчит.

**Разумное сочетание:** нынешний бот как круглосуточный, плагин вторым ботом — когда нужно
вмешаться в конкретную идущую сессию.

## Итоговый план

1. **Claude+Telegram остаётся нативным.** Контейнер лишит его смысла.
2. **Hermes, OpenClaw, Marketing agency, Knowledge Factory — в контейнеры**, каждый со
   своим именем проекта, своей сетью, своим томом профиля.
3. **Связь между ними — через внешние сети**, а не общий профиль.
4. **Каждому боту свой токен.** Единственный неустранимый конфликт.
5. **Управление машиной из контейнеров — через посредника**, не через сокет Docker.
6. **Плагин Telegram — вторым ботом**, если нужно вмешиваться в идущие сессии.
